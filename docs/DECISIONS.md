# 設計と運用の判断

コードの形と作業の進め方についての重要な判断と、その理由。ゲームの仕様（見た目、操作、艦種、作戦）の正本は `docs/spec.md`・`docs/campaign.md`・章のファイル、日ごとの経緯とユーザーの判断の一覧は `docs/history.md`。ここには写さない。理由が資料に残っていないものは「記録なし」と書く。

## コード

| 判断 | 理由 | いつ・出典 |
|---|---|---|
| ビルドしない。ブラウザで `index.html` を開けば動く | 開発中はブラウザで動く形を保ち、販売のときにデスクトップアプリとして包む | 2026-10-01、`docs/roadmap.md`「完成」の定義 |
| ES モジュールでなく、普通の `<script>` を順に読む。`battle/` の外側の名前はファイル間で共有する | `file://` で開けるようにするため | 2026-10-02、`docs/roadmap.md` フェーズ0 |
| ゲームのデータは JSON でなく `data/` の JS ファイル（`window.WOS_DATA`） | JSON は `file://` で読み込めない。コードを触らずに数値と作戦を足せる | 2026-10-02、`docs/roadmap.md` フェーズ0 |
| Three.js は r128 に固定（CDN は cdnjs と jsdelivr の `three@0.128.0`） | 記録なし（最初の試作から r128） | `docs/code.md`「ライブラリ」 |
| 保存は localStorage の `wos.save.v1`。形式を変えたら `migrate()` で古いデータを直す | 遊ぶ人の進行を消さないため | `docs/code.md`「保存」 |
| `package.json` は確認用の道具だけ（Playwright、three） | ゲームはビルドしないので、npm はテストにだけ使う | `package.json` |
| 自動確認はヘッドレス Chromium で、戦闘は `step()` を直接呼んで早送りする | ヘッドレスだと描画が遅い | 2026-10-02、`docs/roadmap.md` フェーズ0 |

## 作業の進め方

| 判断 | 理由 | いつ・出典 |
|---|---|---|
| 正本は GitHub のこのリポジトリ。ブランチを切って PR にし、`main` へ直接 push しない | 変更を確かめてから入れるため | ユーザー決定 2026-10-02 |
| Claude は CI が通ったら随時マージしてよい（squash） | ユーザーの判断 | ユーザー決定 2026-10-02 |
| 試遊は claude.ai の非公開ページ。GitHub Pages は使わない | GitHub Pages は誰でも見られる公開になる | ユーザー決定 2026-10-02 |
| 販売は PC 向けだけ。スマホ向けの調整は足さない | ユーザーの判断（Steam で販売） | ユーザー決定 2026-10-01・03 |
| 見た目は見本の画像を見せ、許可を得てから入れる | ユーザーの判断 | ユーザー決定 2026-10-03 |
| 釣り合わせはその節のデータで行い、共通の値は変えない | ユーザーの判断（「できるだけ基礎の変数は変えないでください」） | ユーザー決定 2026-10-29 |
| `CLAUDE.md` は 7000 バイト以下に保つ（`npm run check-docs`） | 毎回読み込まれるので、短いほどトークンを使わない | `tests/docs-check.cjs` |
| `node_modules` をリンクで置かない（worktree でもそれぞれ `npm install`） | 片付けたときに本体の `node_modules` が消えた | 2026-10-14、`docs/code.md`「確認」 |

## Claude と Codex の併用（2026-10-29）

| 判断 | 理由 |
|---|---|
| Claude Code と OpenAI Codex Cloud を同じリポジトリで使う。共通のルールは `docs/collaboration.md`、Codex の入口は `AGENTS.md` | Claude の利用上限に達しても、Codex で作業を続けられるようにする |
| Codex は PR を作るところまで。マージは Claude かユーザー | ユーザーの判断 |
| ブランチの名前は Claude が `claude/`、Codex が `codex/` で始める | 誰の作業かを一目でわかるようにし、同じブランチに両方が書かないようにする（ユーザーの判断） |
| 作業中の第6節（`feat/denali-feint`）は Claude が続ける | ユーザーの判断 |
| 引き継ぎは「作業中」のコミットの push と、PR の本文の「引き継ぎ」の欄、`docs/PROJECT_STATUS.md` で行う | どちらが急に止まっても、続きが GitHub だけでわかるようにする |
| push したブランチで rebase と force-push をしない。`main` は merge で取り込む | 相手の手元の変更を失わないため |
| 分担: 計画・作業票・レビュー・マージ・資料・試遊ページは Claude、作業票の実装は Codex。小さな修正は Claude が直接行う | トークンを節約するため。実装と早送りの繰り返しは Codex に回し、これまでの判断を知っている Claude が仕様と資料を持つ（ユーザーの判断） |
| 作業票は GitHub の Issue。Codex は結果を最後のコミットの本文に書いて止まり、資料は書かない（Claude がいないときを除く） | リポジトリにファイルが増えない。資料を書くのが1人なら食い違わない（ユーザーの判断） |
| 試遊ページは、Claude がセッションの最初に `main` と比べて載せ直す。待たずに遊ぶときは ZIP を落として `index.html` を開く | 外部サービスやアカウントを増やさずに遅れを小さくする（ユーザーの判断） |
| Codex へはユーザーが貼って渡す（Claude がブランチ・下書きの PR・貼る文を用意し、push を見張る）。`@codex` は使わない | `@codex` で実装を頼むと「環境を作って」と返り、動かなかった（PR #231・#232）。手で貼る形は push まで動いた（ユーザーの判断、2026-10-29） |
