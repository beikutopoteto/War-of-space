# Claude と Codex の共同作業

Claude Code（Claude）と OpenAI Codex（Codex。Codex Cloud か、ユーザーの Mac の Codex CLI）が同じ GitHub リポジトリで作業するときの共通ルール（ユーザー決定 2026-10-29。手元の CLI は 2026-10-30 から）。Claude の利用上限に達したときも、Codex が続きを拾えるようにするのが目的。入口は Claude が `CLAUDE.md`、Codex が `AGENTS.md`。ゲームの仕様と進め方の決まりはどちらも同じ（`docs/spec.md`、`docs/requests.md`）。

## 分担（ユーザー決定 2026-10-29。2026-10-30 に手元の Codex CLI 向けに変えた）
ふだんは、ユーザーの Mac で Claude が Codex CLI を直接呼ぶ（下の「Codex を手元から呼ぶ」）。ユーザーが間に立って作業票を貼る形（「Codex への渡し方（手動）」）は、Codex Cloud を使うときだけ。
- **Claude**:
  - 会話、指示の読み取り、仕様と計画、物語、見た目の見本。
  - 作業票（Issue）を書き、Codex の作業フォルダ（`git worktree`）を作って `codex exec` で呼ぶ。
  - **git は Claude**: コミット、push、PR、マージ。Codex の差分を読み、Codex が測った数のうち大事なものは Claude も早送りで確かめる（下の「Codex への渡し方」のレビュー）。
  - Codex の差分をレビューし、直しが要れば Codex に返して直させる（`codex exec resume`）。
  - 資料に記録する。試遊ページを更新する。
  - **小さな直しも Codex に任せる**（ユーザーの指示 2026-10-30「簡単なテストなども任せてみてください」）: テストの直し、数行のコードの直し、早送りやテストを回すことも Codex に頼む。Claude が自分でやるのは、頼む手間のほうが明らかに大きいとき（1行の打ち間違いなど）と資料だけ。
  - **短い直しは Claude がそのまま直してよい**（ユーザーの指示 2026-10-31「短ければ今回のようにそのまま直して、テストしても構いません」）: 原因を調べるうちに直す場所が分かり、差分が短い（数十行まで）ときは、Codex に渡さず Claude が直してテストまで回す。長い実装・作業票1つ分の変更は今までどおり Codex。
  - **どちらにするかを先に言う**（ユーザー 2026-11-05。同じ日の夕にも、見本から実装へ移るときに言わず「Codex に任せる予定ですか？」と聞かれた。見本の段階から実装に入る一言目で言う）: 実装を始める前に「Claude が直す／Codex に渡す」と理由を一行添える（2026-11-05 は #294〜#296 を一度も渡さず、理由も言わなかった）。境目（新しい機能で、40行を超えそうなもの。例: #296 の技術ツリーのウィンドウ）は Codex に寄せる。Claude が直したときも、`npm test` と早送りは決まりどおり Codex に頼んでよい。
  - **Codex に任せる量は変動制**（ユーザーの指示 2026-10-31）: Claude の週の上限の残りが20%を切ったら（2026-11-04 に15%から変更）、Codex に回す量を増やす（短い直し・テストの直し・早送りも Codex へ。Claude は計画・差分のレビュー・git・資料に絞る）。Claude は残りを自分では見られないので、ユーザーが知らせたとき（`/usage` など）か、Claude Code に上限の警告が出たときに切り替える。
- **Codex**（`gpt-6.1-terra`、推論の強さ medium。sol はまれに。下の「モデル」）:
  - 作業票1つ分のコードとデータの変更。作業フォルダの中だけを直す。
  - 構文の確認（`node --check`）、`npm run check-docs`、早送りの道具（`tools/*.cjs`）、`npm test` を自分で回し、測った数を結果に書く（サンドボックスを緩めた。ユーザー決定 2026-10-30）。
  - 結果（下の「結果」の型）を最後の返事に書いて止まる。コミット・push・PR はしない。
  - 資料の整理はしない（`docs/menu.md` の仮の数値は書いてよい）。

## Codex がチャットの主担当になるときの進め方（ユーザーの指示 2026-11-08）
Claude が利用上限に近づくか上限に達し、ユーザーが Codex と直接開発を続けるときは、通常の「Claude が作業票を渡し、git と資料を担当する」分担に代えて、以下で進める。ブランチ名・マージ・載せ直しも、この場合は以下を優先する。
- この担当変更はユーザーの引き継ぎ指示で始める。通常のClaude主担当の進め方は残す。Codexの入口は `AGENTS.md`、更新前の委託向け原文は `docs/agents/codex-delegated-2026-11-08.md`。元の `CLAUDE.md` を消したり、通常の委託まで直接担当に変更したりしない。
- 優先順位と停止条件は `docs/PROJECT_STATUS.md`。2026-11-08の指示は「チュートリアル・操作方法・演習の修正が先、第二章へ進めない」。第二章は再開指示まで保留する。
- 作業ごとに worktree `~/dev/wos-codex-<話題>`、ブランチ `claude/<話題>` を作る。node_modules は `~/dev/War-of-space/node_modules` へのリンクにする。
- 実画面のテスト（`npm test`）と写真は Chromium を使い、Codex のサンドボックスでは起動できなかった。サンドボックスの外で、ユーザーの許可を得て回すか、ユーザーに回してもらう。
- 各作業で写真の台本（`tools/ground-*-shots.cjs`）を書く。1600×900、出力は `.shots/`、ページの例外があれば失敗にし、写真をユーザーに見せる。
- 実画面のテストでは、ほかの部隊の名札がクリックをさえぎることに注意する。カメラを動かしたら描画の更新を待つ。ボタンは名前の先頭で探し、待ち時間は実際の速さから決める。メニューへはページを開き直してから入る。
- 手元の `npm test` で「第6節」「視点のスティック」が落ちたのは、ほかの重い処理と同時に回したときだけ（再実行・CI で通る）。重い処理を同時に回さない。
- 流れは、ブランチ → 実装 → `npm test` → PR → CI（10〜25分）→ squash マージ。CI が通れば自動でマージしてよい（ユーザー決定）。マージ済みのコミットを含むブランチは `git rebase --onto origin/main <前のブランチ>` で載せ直す。
- ユーザーへの報告は日本語で短く、写真を送る。矛盾や質問はおすすめの案つきで聞く。試遊ページは Codex から更新できないため、ユーザーが Claude に頼むか後回しにする。

- モデルの作り直しのような見た目の作業（2026-11-12〜13）: 形を決めるのは Fable、表への接続・テストの直し・道具は Opus か Codex。見本の形を何度も直すあいだは、ブラウザの長いテスト（`npm run test:ground`）を毎回回さず、`node tests/ground-models.cjs` と `tools/model-floaters.cjs` で確かめ、最後の版で `npm test` を1回回す。形を直すと決まったら、走っているテストは止める（走っている間はファイルを変えない）。
- 見た目の作業から実装へ移る作業票（2026-11-13 #405）: 変える関数・表を使う所を、リポジトリ全体で grep する（`--include='*.js' --include='*.cjs' --include='*.html'`）。変えない所（地上の画面が宇宙の艦の幾何を写す所、準備画面のドック）も作業票に「今のまま」と書き、そのための確かめ（テストの名前）を直さずに通すことを完了の条件にする。
- 大きな作業票（2026-11-14 票3・票4）で Codex を止めないために、作業票に先に書いておくもの:
  - 作り方の決まっていない所（直す所は1か所、判定の場所と順、部品の定義）。
  - 変えてよい期待値の一覧。それ以外は変えずに止める。
  - 作戦を足す作業票では、作戦の一覧を決め打ちしているテストを grep して、変えてよい期待値に入れる。票4は `tests/terrain-check.cjs` の本営の組（同じ地形の作戦の一覧）で止まった。
- Codex に `CLAUDE.md` を直させるときは「行を消さない。7000バイトを超えるなら止めて書く」と書く（2026-11-14 #414 で、上限に合わせるため規則の行が別の行に置き換わっていた）。
- `npm run check-docs | tail -1 && git commit …` のように続けない。`tail` の終了コードで失敗が見えず、そのままコミットされる（2026-11-14）。check-docs は単独で走らせ、結果の行を見てからコミットする。
- 初めの位置の写しで「前と同じ」と出ても、ゲームの中の並べ直し（補給のある作戦の `groundSupplyStartDeploy` が地上の隊を本営へ並べ直す）のせいのことがある。報告には、実際に動いた隊を書く（2026-11-14 #414: 動いたのは航空2隊だけ）。
- 見本のページとゲームの画面は光が違う（2026-11-13: 宇宙の画面は自己発光と光のにじみで、見本で見えていた暗い部品が白く飛びやすい。前の形も同じだった）。採用の写真は、前の形・新しい形を同じ角度で並べて撮り、違いが形によるものか画面の光によるものかを分けてからユーザーに見せる。
- 作業フォルダ（ワークツリー）で `git stash` を使わない（2026-11-13: 変更前の状態と比べようと stash して戻したら、索引が空になり全ファイルが「消した」「追跡していない」に見えた。ファイルは無事で `git reset` で戻った）。前の版と比べるときは別のワークツリーか `git show <commit>:<file>` を使う。
- 採用の表のような「空のときの従来の表示」を前提にしたテストは、表を埋めると落ちる（2026-11-13: 仮の陣営色が文字列だった、戦闘機を3機と決めていた）。表を埋める前に `grep -rn "TEAM_COL:\['blue'" tests` と、機数や形を固定した確かめを探す。

## サブエージェント（Claude Code。2026-11-07 に CLAUDE.md から移した）
- 範囲がはっきりした実装はサブエージェント `wos-dev` に任せてもよい（機能追加・バグ修正・数値調整を、ヘッドレス Chromium での確認まで）。小さな直しの分け方（短い直しは Claude、週の上限が残り20%を切ったら Codex を増やす）は上の「分担」。
- 物語の土台固め（新しい設定の物理と食い違いの考証、叩き台）はハードSF作家の `wos-story`。会話の案はリコ軍曹の通信の形（`docs/riko.md`）。
- 敵と味方の部隊の動き・戦闘の規模と長さはストラテジーの専門家の `wos-strategy`、数値の釣り合い（長さ・数・硬さ）はバランスの専門家の `wos-balance`。
- `wos-story`・`wos-strategy`・`wos-balance` は案を返すだけ。資料には Claude が書く。
- CPU の動きの問題（固まる、群がる、棒立ち）の解決と評価は `wos-ai`（コードを直す）。
- 定義は `.claude/agents/*.md`。ユーザーの新しい決まり（変えてはいけない値、好む作戦や動き、測り方）は `/tidy-docs` で該当する定義へ足す。

## 作業票（GitHub の Issue）
Claude が書く。題は「作業票: <話題>」。本文の型:

```
## 目的
## 触ってよいファイル
## 変えてはいけないもの（ユーザーが決めた仕様、全作戦で共通の値など）
## 完了の条件（例: オートモードで半分以上勝つ、npm test が通る）
## 届かないとき（調整してよいものと順番、上下の幅。それでも届かなければ止めて結果に書く）
## 確かめ方（コマンド、見る数字）
## 参考（読む資料の場所。必要な部分だけ）
```

作業票で決めておくこと（Codex の要望 2026-10-30、#239 の結果）:
- 測り方: 完了を判定する道具と遊び方（`denali-sim` の auto は駐屯隊35隻のまま、`length-sim` の auto は出撃の上限まで写す、のように母集団が違う）。「何もしない」はどの道具のどの引数か（`length-sim` か `op-sim` の idle）。
- 数え方: 「長さ」は `gameSec`（1倍速の換算）で、早送りにかかった壁時計の時間ではない。中央値は全回か勝った回か、範囲はすべての回か中央値か。
- 順番と前提: 出来事の順番（波の順など）と、目標をどの段階で作るか。仮説（「これを直せば届く」）は仮説と書く。
- 原因を切り分ける数: 隻数だけでなく耐久の残りなど、結果の表に出してほしい項目。
- 戦いの流れに頼るテスト（ある場面が来るのを待つ確認）: 数値や撃ち方を変える作業票では、前からある確認がその場面を観測できなくなることがある（2026-11-06 #331 で3件）。場面をテストの中で作り直してよい、と書いておく。

Codex は終えたら、最後のコミットの本文に結果を書く（Claude は `git log` で読む。Issue にコメントできるならそこにも）:

```
## 結果
- PR: #番号（ブランチ codex/<話題>）
- やったこと:
- 測った数字:
- 作業票と違うこと・その理由:
- 自分で置いた仮の数値:
- 残った問題・わからないこと:
- テスト: npm test の結果
- 試遊ページの更新: 要る / 要らない
```

Claude はこれを読んでレビューとマージを行い、仮の数値と決まったことを資料（`docs/menu.md`、`docs/roadmap.md` ほか）に書いてから、Issue を閉じる。

## Codex を手元から呼ぶ（2026-10-30。ユーザーの Mac）
ユーザーの Mac では、Claude が Codex CLI を直接呼べる（作業票を貼る手間がない）。手動の渡し方（下）は、Codex Cloud を使うときに残す。
- 置き場所: リポジトリは `~/dev/War-of-space`。Codex CLI は `~/.npm-global/bin/codex`（ChatGPT でログイン済み）、`gh` は `~/.local/bin/gh`（PATH は通していないのでフルパスで）。push はこのリポジトリだけの設定（`credential.https://github.com.helper` に `gh auth git-credential`）。
- モデル（ユーザー決定 2026-10-31）: 基本はいつも `gpt-6.1-terra`（#267 の AI の直し程度まで）。`gpt-6.1-sol` は使える量がずっと少ないので、作業票を正確に書き直して頼んでも terra がつまずいたときか、ユーザーが言ったときだけ。使ったら作業票と報告に理由を一言書く。推論の強さはどちらも medium。terra の出来が悪いときは、まず作業票の書き方（測る数・方向・やめどき）を疑う。
- 手順:
  1. Claude が作業票を書く（GitHub の Issue。型は上の「作業票」）。
  2. Claude が `git worktree add -b codex/<話題> ~/dev/wos-codex-<話題> origin/main` で Codex 専用の作業フォルダを作る（Claude の作業と混ざらない）。
  3. Claude が後ろで走らせる: `codex exec -m gpt-6.1-terra -c model_reasoning_effort="medium" -C ~/dev/wos-codex-<話題> -s danger-full-access -o <結果のファイル> "<作業票の番号と、読むもの・守ること>" < /dev/null`。
  4. **コミットは Claude がする**: Codex は作業フォルダを直し、早送りとテストを自分で回して、結果（「結果」の型）を最後の返事に書いて止まる。Claude は差分を読み、大事な数は早送りで確かめる。
     - サンドボックスは `danger-full-access`（ユーザー決定 2026-10-30「緩めます」）。前の `workspace-write` では Chromium が起動せず（`browserType.launch` が閉じる）、`.git` にも書けなかった（`index.lock` を作れない）。緩めても、作業フォルダの外を直すこと・コミット・push は作業票で禁じる。直しが要れば、測った数を添えて `codex exec resume --last`（作業フォルダで）で続きを頼む。よければ Codex の結果を本文にしてコミット・push・PR・マージ・資料・試遊ページまで進める。
  5. 終わったら `git worktree remove` で作業フォルダを片付ける。
- `npm test`（約20分）と早送りの道具は、Claude と Codex で同時に回さない（実時間に頼る確認が落ちる）。
- 見た目の変更は、ユーザーが変える場所を全部見終えてから `npm test` を回す（2026-11-05: 左上を入れてテストを始めたら右上の作り直しを頼まれ、2回止めた）。
- 見本は、実際の戦闘画面を `tools/browser.cjs` で開き、HTML と CSS を重ねて撮ると早い（2026-11-05。中身を本物のまま枠だけ変える見本は、本物の要素に CSS を足して撮る）。Codex に走らせる回は、Claude は待つ。
- Codex に回させる道具は、リポジトリの `tools/` に置く（2026-10-30: Claude のスクラッチパッドに置いた道具がいつの間にか消え、Codex が回せずに止まった）。
- 「撃たない」「狙わない」を確かめるときは、狙いの標本ではなく打撃で数える（`damage` を包む。2026-10-30 #254: 狙いの標本では1件だったが、打撃で数えると小型機の射撃と残った `fireTarget` の2つの道が見つかった）。
- 続きを頼む `codex exec resume --last` は `-s` を受け付けない（2026-10-30 に起動せず終わった）。作業フォルダの中で `-c sandbox_mode="danger-full-access"` を付けて呼ぶ。
- 何か所にも効く仕組み（時計、保存の形など）を足す作業票には、作り方を先に決めて書く（2026-11-05 #316: 「段10 まで時計を止める」だけ書いたら、`gameSec` が索敵と交戦にも使われていると分かって Codex が実装せずに止まった。「停止秒を引いた `opClock()` に置き換える」と書いて続きを頼むと、1回で最後まで進んだ）。
- 作業票に今の決まりを書くときは、資料の古い記述を写さない（2026-11-01: 「陽動は触れる隊だけが撃つ」と古い決まりを書いたら、Codex が撃つ隊を減らし、守備隊を剥がせなくなった。今は #248 で全隊が撃つ）。動きの決まりはコードを grep して確かめてから書く。
- 作戦の時刻と分の換算は、その作戦の始まりの時刻から数える（2026-11-01: 第6節は 13:00 起点で、14:10 は 70。80 と書いて 14:20 になった）。作業票には分と時刻を両方書き、合っているか確かめる。
- ユーザーが先に遊びたいとき（2026-11-01）: Codex は実装と `node --check`・`npm run check-docs` だけで止め、Claude が試しのページ（いつものとは別 URL）に載せる。動きを何度か直したあとで、まとめて `npm test` と早送り。テストの前提が古くなったものはテストを直し、場面が戦闘の損害で崩れるならテストの中で場面を作る。
- `codex exec` は後ろにも `; echo` などを付けない（2026-10-31: 付けたら許可のルールの形から外れ、安全チェックに止められた。付けずに呼び直すと通った）。
- `codex exec` と git は、先頭に `cd … &&` を付けずに呼ぶ（`codex exec -C <作業フォルダ>`・`git -C <作業フォルダ>`）。付けると `開発環境/.claude/settings.local.json` の許可の型に合わず、オートモードの安全チェックに止められる（2026-10-31）。
- Codex を走らせたあとに作業票へ足したコメントは、Codex に届かない。足すなら止めて呼び直すか、終わってから続きとして呼ぶ（2026-10-31）。

- 作業フォルダは `git worktree add -b <ブランチ> ~/dev/wos-<話題> origin/main` で作り、最初の push で `-u` を付ける（2026-11-05: `org-names` が自分のブランチではなく `origin/main` を追っていた）。
- マージ:
  - Claude: CI が通ったら squash でマージしてよい（ユーザー決定 2026-10-02）。手順は `/ship`。

## 変更の受け渡し
- 止まる前（区切りごと、利用上限が近いとき、セッションを終えるとき）に、作業中の変更を「作業中: …」のコミットにして push する。未コミットのまま残さない。
- PR を作る（できあがっていなければ下書きの PR）。本文の最後に「引き継ぎ」の欄を書く:

```
## 引き継ぎ
- 担当: Claude / Codex
- 状態: どこまでできたか（最後のコミット）
- 次の一手:
- 未確認・気になること:
- テスト: npm test の結果（未実行ならそう書く）
- 試遊ページの更新: 要る / 要らない
```

- 受け取る側（Claude が上限で止まった作業を Codex が続けるときなど）: `git fetch origin` → `git switch <ブランチ>` → `git merge origin/main` → PR の「引き継ぎ」と `docs/PROJECT_STATUS.md` を読んでから続ける。引き継ぐときは PR の担当の行を書き換える。
- マージしたら `docs/PROJECT_STATUS.md` の「作業中のブランチ」から消す。

## 変更を失わないために
- 作業を始める前に `git status` と `git fetch origin`。未コミットの変更があれば、何のものか確かめてからにする（消さない）。
- push したブランチで rebase、amend、force-push をしない。`main` は `git merge origin/main` で取り込む。取り込む前にコミットする（2026-11-05: stash → ff → stash pop で作業フォルダの index が空になり、全部のファイルが「削除」と「未追跡」に出た。`git reset` で直った）。
- 相手が担当しているブランチには、引き継いだときだけコミットする。
- 食い違いやすいのは資料（`docs/history.md`、`docs/roadmap.md`、`docs/menu.md`、`docs/campaign.md`）と `tests/smoke.cjs`。資料への追記は、マージの直前にまとめて行うと食い違いが減る。
- `package-lock.json` は手で直さず、`npm install` で作り直す。
- `git reset --hard`、`git clean`、`git checkout -- .` は、未コミットの変更がないことを確かめてからだけ使う。

## 試遊ページ（ユーザー決定 2026-10-29）
- 更新は Claude だけができる（claude.ai の非公開ページ）。Codex がゲームの中身を変えたときは、PR と作業票の結果に「試遊ページの更新が要る」と書く。
- Claude はセッションの最初に、試遊ページに載っているファイル（Artifact の `read`）と `main` を比べ、違えば載せ直す。Claude がいないあいだの遅れは、これで取り戻す。
- 待たずに遊ぶときは、GitHub でブランチを選び「Code → Download ZIP」で落とし、展開した `index.html` を開く。ビルド不要なので、`main` でも作業中のブランチでもそのまま動く（three.js を CDN から読むのでネット接続は要る）。
